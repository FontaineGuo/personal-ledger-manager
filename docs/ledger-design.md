## 1. 背景

用户目前以 Excel（2026下半年.xlsx）手工维护个人账本：三张工作表（交易流水 / 余额快照 / 配置表），月度对账，账期随工资发放日切分。手工记账的痛点：

- 每笔需手动填 7 个字段，移动端编辑不便；
- 月末勾稽靠人肉核对，易漏补差（如"11月微信补差 0.61"）；
- 查询复盘需手工筛选透视，无法随口提问。

本设计书提出**基于对话的记账流程**：用户用一句自然语言（"午饭晚饭一共 58，微信"）完成记账，AI 负责意图解析、槽位补全、确认回显、落库校验与月度复盘。范围覆盖快速记账、信用卡分期备注、投资转入、报销、AA、月度对账、自然语言查询、微调共 8 个核心用例（U1~U8，见 t1 §2）。

## 2. 现状分析

### 2.1 现有账本结构（实测）
- **交易流水**（A1:G287）：日期｜账期｜方向(收入/支出)｜分类｜金额｜账户｜备注
- **余额快照**（A1:D49）：账期｜账户｜月初余额｜月末余额（9 账户 × 5 账期）
- **配置表**（A1:C10）：支出分类/收入分类/账户列表三列白名单

### 2.2 关键业务规则（实测归纳）
- **账期 ≠ 自然月**：切换点在每月末工资发放日附近（如 6/25 工资归 2026-06）。
- **扁平单级分类**：支出 9 类（数码电器/日用百货/餐饮美食/交通出行/文化休闲/医疗健康/旅行/投资/杂项），收入 5 类（工资收入/股权收入/投资收益/额外/其他/报销收入）；粒度靠备注补充。
- **8 账户**：中行、招行、建行、农行、成都银行（银行卡）+ 微信余额、支付宝余额、余额宝（支付账户）。流水集中在中行(164)、微信(71)、招行(37)。
- **信用卡分期**：招行大额以备注前缀 `信用卡分期：` 标识，一次性全额入账，不拆期数（既有简化，本期沿用）。
- **月末勾稽**：月末余额 = 月初余额 + 当期流入 − 流出；微信存在小额"补差"调整。

### 2.3 痛点 → 设计目标
| 痛点 | 设计目标 |
|------|---------|
| 逐字段手填 | 一句话记账，AI 补全默认值，只追问关键缺失项 |
| 重复误记 | 数据库级幂等指纹，重复提交需确认 |
| 月末对账费时 | 一条"对账"指令自动勾稽并报告差异明细 |
| 查询不便 | 自然语言查询（"这个月餐饮花了多少"）与月度复盘推送 |
| 看不清钱花哪了/Excel 习惯 | 账目细节可视化（分类构成/趋势/账户流/日分布）+ 三表同构与报表双路 Excel 导出（§4.3 report*/export* 接口族） |

## 3. 总体架构

```
┌────────────────────────── 对话环境 ──────────────────────────┐
│   主环境：DSH Web GUI（自然语言对话 / 卡片确认 / 截图OCR）      │
│   进阶通道：Claude Code skill（缩写命令 / 批量录入 / 月结）      │
└──────────────┬───────────────────────────────────────────────┘
               │ 统一记账接口（t2 §3，11 个函数）
┌──────────────▼───────────────┐   ┌──────────────────────────┐
│   记账服务层（ledger CLI）     │   │  导出：exportToXlsx()     │
│  意图/槽位解析 → 校验 → 事务   │   │  （与旧 xlsx 同构，供     │
│  白名单 / 幂等 / 勾稽 / 封账   │   │   Excel 人工查看）        │
└──────────────┬───────────────┘   └──────────────────────────┘
               │ SQL
┌──────────────▼───────────────┐
│  存储：SQLite data/ledger.db  │  transactions / accounts /
│  每日自动备份 backups/*.db     │  categories / balance_snapshots
└──────────────────────────────┘
```

要点：
- **存储选 SQLite**（选型对比见 t2 §1：对比 xlsx / JSONL，SQLite 在对话写入安全、幂等约束、聚合查询上全面占优，迁移成本一次性）；
- 对话环境与记账服务解耦：DSH 与 Claude Code 共用同一接口与数据，协议一致；
- xlsx 保留为**导出格式**，迁移过渡期双跑核对一个月。

## 4. 数据设计

### 4.1 表结构（详细 DDL 见 t2 §2）

**transactions（交易）**：id, date, period(账期), direction(**收入/支出/内部转账**), category, amount, account, **transfer_to(转账转入方，仅内部转账)**, note, source(chat/import/adjust), session_id, created_at, **fingerprint（唯一索引，幂等防重）**。

**内部转账设计**：账户间流转（工资卡→零用卡、活期→余额宝）单笔记录、双账户字段；自动排除于收支统计与分类排行（不虚增虚减结余），对账视图拆双边（转出=流出、转入=流入）保证两账户勾稽平衡；转入表外（证券等）仍记支出-投资。迁移时把"转余额宝"类旧记录重 classified 为内部转账。

**accounts（账户）**：name(主键), kind(bank/wallet), aliases(JSON 别名，供槽位推断), active。

**categories（分类配置）**：(name, direction) 联合主键 + aliases(JSON 别名) + active——方向由分类联动推断，杜绝"工资收入"出现在支出方向；停用只退出白名单，历史交易不受影响。

**balance_snapshots（月度快照）**：(period, account) 主键，opening / closing（人工抄录真值锚点）/ closed（封账标志）。

### 4.2 校验与对账设计
1. **白名单校验**：分类、账户必须在配置表内；新分类需用户确认后写入。
2. **幂等防重**：`fingerprint = hash(方向|日期|金额|账户|分类|备注规范化)`，唯一索引 + 插入前查询，命中则回显已有记录要求确认。
3. **余额勾稽**：`closing = opening + Σ收入 − Σ支出`（SQL 视图 v_period_flow 聚合），差异 >0.01 元报告差异明细。
4. **封账**：对账通过后 closed=1，封账账期禁止补插；补差类微调走 source='adjust' 并重新开账。
5. **金额合法性**：0 < amount < 1,000,000，两位小数；快照 opening 自动接力上一账期 closing。

### 4.3 接口清单（函数签名级，见 t2 §3）
- 写入：`addTransaction`（含 confirm 幂等确认）、`addTransfer`（内部转账，白名单账户间）、`upsertSnapshot`、`reconcilePeriod`、`closePeriod`
- **纠错**：`updateTransaction` / `voidTransaction`（软删留痕）/ `reopenPeriod`（封账后纠错需先重开账，改完重新对账封账）
- **配置维护**：`addCategory` / `addAccount`（含别名登记）、`setCategoryActive` / `setAccountActive`（停用/启用，不影响历史交易）、`renameCategory` / `renameAccount`（改名迁移历史引用，旧名转别名）、`addAliases`（槽位推断别名维护）、`listConfig`（含停用项）
- 查询：`queryTransactions`、`summaryPeriod`、`getCategoryWhitelist`
- **可视化报表**（chart-ready JSON，接口与渲染解耦，为未来可视化前端预留统一出口）：`reportCategoryBreakdown`（分类构成饼图）、`reportTrend`（月度趋势）、`reportAccountFlow`（账户资金流）、`reportDailySpend`（日消费分布）、`reportDetail`（明细表分页）、`reportPeriodCompare`（环比复盘）
- **导出**：`exportToXlsx`（三表同构）、`exportReportToXlsx`（报表 Excel 版：透视/趋势/明细含合计行）
- 导出：`exportToXlsx`

## 5. 对话交互流程设计

### 5.1 五步对话协议

```
用户输入 → ①意图识别 → ②槽位抽取 → ③缺失槽位追问 → ④确认回显 → ⑤落库+校验
```

- **意图**：记支出/记收入/**内部转账**（白名单账户间流转）/报销到账/查询/对账/修正/**配置管理**（加分类/加账户/停用/改名/加别名，见 t3 §4）。
- **槽位**：date、period、direction、category、amount、account、note。
- **默认与推断**：date 缺省今天；period 默认 date 所在月，月末工资周交易追问；direction 由分类联动；category 映射白名单，不在则追问；account 由支付方式词推断，缺省给最常用建议项。
- **追问原则**：一次只问最关键缺失槽位，给带默认值的封闭式选项；金额缺失必问。
- **确认回显**：七字段紧凑卡片，推断项标 *，用户回"对/改X"。
- **幂等**：重复提交相同指纹 → "疑似重复，确认再记？"

### 5.2 场景示例（完整对话见 t3 §1.2）
| 场景 | 用户说 | 关键处理 |
|------|--------|---------|
| A 快速记账 | "午饭和晚饭一共 58，微信" | 合并备注、一步确认落库 |
| B 信用卡分期 | "招行信用卡分期买了漫步者耳机 1299，分12期" | 生成"信用卡分期："前缀备注，MVP 一次性入账并明示 |
| C 报销 | "出差打车 320 的报销到账了，招行" | 方向联动 → 收入-报销收入 |
| D 投资转入 | "转 5000 到余额宝买理财" | 识别为支出-投资而非消费，确认转出账户 |
| E AA 代付 | "昨天晚饭饭AA" | 追问金额/账户，只记本人份额 |
| F 补差微调 | "微信补差 0.61，11月" | 跨月账期确认，source=adjust |

### 5.3 查询与月度复盘
- 自然语言查询：翻译为 queryTransactions/summaryPeriod 参数，返回带笔数、笔均、环比的摘要。
- 月度复盘：账期结束首次对话主动触发，菜单式提供分类排行 / 环比 / 账户勾稽 / 投资报销台账；勾稽发现差异时**直接给出修正入口**（"回复'记一笔补差'即可生成修正"）。

## 6. DSH vs Claude Code 实施路径对比

| 维度 | DSH（Web GUI + run_code）——主环境 | Claude Code（CLI + skill）——进阶通道 |
|------|-----------------------------------|--------------------------------------|
| 触发 | 浏览器对话自然语言即用，可贴账单截图 OCR | 终端命令 / slash command |
| 工具链 | run_code 直连 Python，读写校验一体 | 文件编辑 + shell，skill 封装记账宏 |
| 交互 | 富卡片确认、选项按钮、内嵌表格，适合逐笔确认 | 纯文本快捷，适合熟练后缩写语法（"l 餐饮 58 微信"） |
| 长对话复盘 | 会话上下文长，月度复盘体验好 | CLAUDE.md 常驻规则稳定，长对话弱 |
| 随手记 | 浏览器随手开、拍照 OCR 是独有优势 | 需终端环境 |

**推荐**：主环境 DSH Web GUI（最契合对话式记账+月度对账），Claude Code skill 作熟练后的快捷/批量/定时通道；两环境共用同一数据存储与白名单规范，对话协议统一。

## 7. 分期开发建议（MVP → 进阶）

### 第一期 MVP（约 1~2 周）
1. **迁移**：脚本导入旧 xlsx → ledger.db（验收：286 笔核对、5 账期勾稽全平、指纹去重冒烟——见 t2 §4）。
2. **核心接口**：addTransaction / queryTransactions / summaryPeriod / getCategoryWhitelist / exportToXlsx，以及**配置维护一组**（addCategory/addAccount/addAliases/listConfig/setCategoryActive/setAccountActive——支持随时扩展分类与账户）。
3. **DSH 对话协议 MVP**：五步管线 + 场景 A/C/D/F/J/K（快速记账、报销、投资转入、补差、内部转账、表外区分）+ 配置管理对话（场景 G/H）+ 可视化与导出对话（场景 L/M：MVP 先出文本表格+Excel 文件，图表卡片随二期渲染增强）。
4. **月末对账**：upsertSnapshot + reconcilePeriod + closePeriod，差异报告。

### 第二期（熟练后，约 1 周）
5. Claude Code skill：缩写命令、CLAUDE.md 固化规则、批量录入、定时月结。
6. **可视化增强**：DSH 卡片渲染 t2 `report*` 接口（饼图/趋势/日历热力/明细表格），Excel 报表导出（透视/趋势）；账单截图 OCR 记账。

### 进阶项（按需）
7. 信用卡分期拆期计划（当前沿用一次性入账简化，如需逐月摊销再立项）。
8. 多级分类、预算管理、多币种、Web/移动端独立界面。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 对话重复记账 | 数据失真 | 指纹唯一索引 + 命中确认（t2 §2.5），双保险 |
| 账期切分误判（月末工资周） | 月度报表错期 | date≥25 日追问账期；period 显式可覆盖 |
| 分类/账户推断错误 | 脏数据 | 白名单硬校验，歧义必问不猜测，推断项回显标 *，**逐笔确认后才落库**（t3 §5 铁律） |
| 落库后发现记错 | 无法纠正 | updateTransaction/voidTransaction 纠错接口 + 封账后 reopenPeriod 流程 |
| 批量录入绕过确认 | 批量误记 | 批量必须先出预览清单、用户确认后原子落库，禁止静默批量写入（t3 §5-4） |
| SQLite 对用户不透明 | 失去 Excel 直查习惯 | exportToXlsx 保留同构报表；过渡期双跑核对一个月 |
| AI 解析歧义（金额/账户） | 误记 | 追问优先于猜测；金额缺失必问 |
| 备份缺失 | 数据丢失 | 每日自动备份保留 30 天；封账机制限制误改 |
| 分期语义简化 | 长期负债视图不准 | MVP 明示"一次性入账"；进阶期再立项拆期 |
