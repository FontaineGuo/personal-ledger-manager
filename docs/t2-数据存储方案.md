# t2 数据存储与读写方案（基于 t1 财务需求规范）

> 输入：docs/t1-财务需求规范.md、2026下半年.xlsx 实测结构
> 实测表结构：交易流水 A1:G287（日期/账期/方向/分类/金额/账户/备注）、余额快照 A1:D49（账期/账户/月初余额/月末余额）、配置表 A1:C10（支出分类/收入分类/账户列表）

## 1. 存储选型对比

| 维度 | 继续 xlsx | SQLite（推荐） | JSONL |
|------|-----------|----------------|-------|
| 数据规模 | 286 笔/半年，个人账本量级下三者均可 | 完全够用，可存数十年 | 同左 |
| 迁移成本 | 零（现状即此） | 一次性脚本导出 3 张表 → 3 张表，约 1~2 小时开发 + 人工核对 | 最低，但余额快照/配置表是结构化二维表，需扁平化再解析 |
| 对话场景写入 | 需整簿读写，并发写易损坏文件；公式/合并单元格脆弱 | 单条 INSERT，事务原子，天然幂等安全 | 追加一行即可，最简单；但查询/更新需全文件扫描 |
| 查询能力（U6/U7 对账、自然语言查询） | 需整表载入后自写聚合 | SQL 聚合一等公民：`SELECT account, SUM(amount)...`，对账/月度汇总天然支持 | 全靠应用层代码，重复造轮子 |
| 幂等/唯一约束（t1 §3.3） | 无约束，靠脚本自查 | UNIQUE 索引 + INSERT OR 判重，数据库级保证 | 应用层手工判重，易漏 |
| 人工直接查看/编辑 | 最强（Excel 打开即用） | 弱（需工具导出） | 中 |
| 可导出兼容 | — | 随时可导出回 xlsx 报表（保留人工查看习惯） | — |

**结论：推荐 SQLite（单文件 ledger.db），理由：**
1. 对话式记账的核心风险是**重复写入与写坏文件**，SQLite 事务 + 唯一索引直接解决；
2. U6 月度对账、U7 自然语言查询本质是聚合查询，SQL 是零成本路径；
3. 迁移成本一次性且低（3 张表结构一一对应，无关系重构）；
4. JSONL 仅当存储永远是"只追加、少查询"时才占优；xlsx 保留为**导出报表格式**而非存储格式。
- 文件位置建议：`data/ledger.db`，与旧 xlsx 并存一个过渡期，双跑核对一个月后 xlsx 转为只读存档。
- 备份策略：每次写入事务提交后由工具自动复制 `ledger.db → backups/ledger-YYYYMMDD.db`（每日一份，保留 30 天）。

## 2. 表结构 Schema 与对账/幂等设计

### 2.1 transactions（交易表，对应"交易流水"）

```sql
CREATE TABLE transactions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  date        TEXT    NOT NULL,             -- ISO YYYY-MM-DD
  period      TEXT    NOT NULL,             -- 账期 YYYY-MM（可≠date所在月）
  direction   TEXT    NOT NULL CHECK (direction IN ('收入','支出','内部转账')),
  transfer_to TEXT    DEFAULT NULL,         -- 仅 direction='内部转账' 时必填：转入账户（account 为转出方）
  category    TEXT    NOT NULL,             -- FK→categories（软校验）
  amount      REAL    NOT NULL CHECK (amount > 0 AND amount < 1000000),
  account     TEXT    NOT NULL,             -- FK→accounts（软校验）
  note        TEXT    DEFAULT '',
  source      TEXT    DEFAULT 'chat',       -- chat / import / adjust（区分对话录入与迁移导入）
  session_id  TEXT    DEFAULT '',           -- 产生该笔的对话会话 id（幂等排查用）
  created_at  TEXT    NOT NULL DEFAULT (datetime('now','localtime')),
  -- 幂等指纹：同指纹 60 秒内重复 → 拒绝并要求确认（t1 §3.3.3）
  fingerprint TEXT NOT NULL,
  CHECK (direction != '内部转账' OR (transfer_to IS NOT NULL AND transfer_to != account))
);
CREATE UNIQUE INDEX ux_tx_fp ON transactions(fingerprint);
CREATE INDEX ix_tx_period ON transactions(period, account);
CREATE INDEX ix_tx_date   ON transactions(date);
```

- **fingerprint = hash(direction | date | amount(2位) | account | transfer_to | category | note_normalized)**（转账含转入方），note_normalized 为去空格小写。插入前 `SELECT id FROM transactions WHERE fingerprint=?`，命中则把已有记录回显给用户确认，不静默插入。
- t1 要求"60 秒内"窗口：实现上命中指纹即人工确认（比时间窗更保守、实现更简单），确认后允许追加第二笔（同日同餐两笔金额相同属合理场景，靠确认而非硬拒绝）。

### 2.4 balance_snapshots（月度快照，对应"余额快照"）

```sql
CREATE TABLE balance_snapshots (
  period       TEXT NOT NULL,             -- YYYY-MM
  account      TEXT NOT NULL REFERENCES accounts(name),
  opening      REAL NOT NULL,             -- 月初余额
  closing      REAL NOT NULL,             -- 月末余额（人工抄录值，作为真值锚点）
  closed       INTEGER NOT NULL DEFAULT 0,-- 是否已对账封账
  PRIMARY KEY (period, account)
);
```

### 2.5 对账与勾稽设计（U6/U8）

- **勾稽视图**（内部转账拆双边：转出方计流出、转入方计流入，两账户均勾稽平衡）：
  ```sql
  CREATE VIEW v_period_flow AS
  SELECT period, account,
         SUM(CASE WHEN direction='收入' OR (direction='内部转账' AND transfer_to=account)
                  THEN amount ELSE 0 END) AS inflow,
         SUM(CASE WHEN direction='支出' OR (direction='内部转账' AND account=transfer_to_ref)
                  THEN amount ELSE 0 END) AS outflow
  FROM (SELECT *, account AS transfer_to_ref FROM transactions)
  GROUP BY period, account;
  -- 注：实现时用 UNION ALL 两段（转出边/转入边）更清晰，语义同上
  ```
- **收支统计排除内部转账**：summaryPeriod 的 byCategory / netIncome 不含 direction='内部转账' 的记录（分类恒为"内部流转"，不可改），避免虚增收支；账户维度流水（byAccount）正常含两端。
- **对账查询**：`closing_expected = opening + inflow − outflow`，与 `closing` 比较，差异 > 0.01 元即报告差异明细（含该账期该账户全部交易清单供逐笔核对）。
- **封账**：对账通过后 `closed=1`；封账账期内禁止再插入该 (period, account) 的交易，微调（U8 补差）走 `source='adjust'` 且需重新开账 → 修改快照 → 重新对账。
- **初始 opening 接力**：新账期 opening 默认 = 上一账期 closing，缺失上一账期快照时由对话提示补录。

## 3. 读写接口设计（Claude Code skill 级）

建议实现为一个 Claude Code skill `ledger`，底层是一个 Node/Python CLI（`ledger.ts` 或单文件脚本），AI 通过函数调用使用。全部函数**返回结构化 JSON**，便于对话回显与追问。

### 3.1 写入类

```ts
// 记一笔。白名单不符→返回 {ok:false, reason:'category_invalid', candidates:[...]} 由对话追问
// 指纹命中→返回 {ok:false, reason:'duplicate', existing: Transaction}，参数 confirm=true 才落库
// 内部转账：工资卡→零用卡、活期→余额宝等白名单账户间流转。
// 两账户均需 active 白名单且互不相同；不产生收支统计，只影响两账户余额与勾稽
addTransfer(input: {
  date?: string; period?: string;   // 默认同 addTransaction
  from: string; to: string; amount: number;
  note?: string; sessionId?: string; confirm?: boolean;
}): Result<{ id: number } | ValidationError>

addTransaction(input: {
  date?: string;            // 默认今天
  period?: string;          // 默认 date 所在月，可显式覆盖
  direction: '收入' | '支出';
  category: string;
  amount: number;
  account: string;
  note?: string;
  sessionId?: string;
  confirm?: boolean;        // 幂等确认标志
}): Result<{ id: number; balanceEffect: { account: string; delta: number } } | ValidationError>

// 月末录入快照并立即执行勾稽校验
upsertSnapshot(input: { period: string; account: string; opening: number; closing: number }):
  Result<{ reconcile: { expectedClosing: number; diff: number; balanced: boolean } }>

// U6 对账：返回每账户差异及明细
reconcilePeriod(period: string): Result<{
  accounts: { account: string; opening: number; inflow: number; outflow: number;
              expectedClosing: number; recordedClosing: number; diff: number }[];
  balanced: boolean;
}>

// 对账通过后封账
closePeriod(period: string): Result<{ closedAccounts: string[] }>

// ===== 纠错类（确认落库后发现记错时使用）=====
// 改一笔：返回修改前后对照供对话回显；封账账期拒绝并提示先 reopenPeriod
updateTransaction(id: number, patch: Partial<{
  date: string; period: string; direction: '收入'|'支出'|'内部转账';
  category: string; amount: number; account: string; transfer_to: string; note: string;
}>): Result<{ before: Transaction; after: Transaction }>

// 作废一笔：软删除（voided 标记，不物理删除），对账/统计自动排除；封账账期拒绝
voidTransaction(id: number, reason?: string): Result<{ voided: boolean }>

// 封账后纠错流程：reopenPeriod(period) → update/void 或补插 → 重新 reconcilePeriod → closePeriod
reopenPeriod(period: string): Result<{ reopenedAccounts: string[] }>
// 配套：transactions 增加 voided INTEGER DEFAULT 0（软删标记），voided=1 不参与勾稽与统计

// ===== 配置维护（新分类/新账户，需对话确认后调用）=====
// 新增；同名/同别名已存在且 active → 返回 {ok:false, reason:'exists'}；已停用则复活并提示
addCategory(name: string, direction: '收入' | '支出' | '内部转账', aliases?: string[]): Result<{}>
addAccount(name: string, kind: 'bank' | 'wallet', aliases?: string[]): Result<{}>

// 停用/启用：停用只退出白名单与推断，不影响历史交易与统计
setCategoryActive(name: string, direction: '收入' | '支出' | '内部转账', active: boolean): Result<{}>
setAccountActive(name: string, active: boolean): Result<{}>

// 改名：全量替换并迁移历史交易引用（事务内 UPDATE transactions 同步），旧名自动加入 aliases 保持旧说法可用
renameCategory(oldName: string, newName: string, direction: '收入' | '支出' | '内部转账', ): Result<{}>
renameAccount(oldName: string, newName: string): Result<{}>

// 别名维护：追加（append=false 时为全量替换）；槽位推断据此映射，是"新配置加了好使"的关键
addAliases(target: { type: 'category'; name: string; direction: '收入' | '支出' | '内部转账' } | { type: 'account'; name: string },
           aliases: string[], append?: boolean): Result<{ aliases: string[] }>

// 列表：含停用项（标 active），供"我的分类/账户有哪些"查询与配置管理对话
listConfig(): Result<{ categories: { name: string; direction: string; aliases: string[]; active: boolean }[];
                      accounts: { name: string; kind: string; aliases: string[]; active: boolean }[] }>
```

### 3.4 对话流程接入要点
1. **录入流程**：AI 解析一句话 → 补齐默认值 → 调 `getCategoryWhitelist` 校验 → `addTransaction` → 回显"已记：10-29 午餐 餐饮美食 ¥25 微信余额"，失败原因驱动追问。
2. **重复防护**：`duplicate` 响应时 AI 展示已有记录并问"是否再记一笔相同的？"，用户确认后带 `confirm:true` 重调。
3. **月末流程**：用户说"对账" → `reconcilePeriod` → 逐账户播报差异 → 平了调 `closePeriod`。
4. **MVP 不做**：分期拆期、多级分类、多币种、预算（与 t1 §3.4 一致）。
