# t3 对话式记账交互流程设计

> 依据 docs/t1-财务需求规范.md（U1~U8 用例、白名单、账期与勾稽规则）。
> 目标：用户用一句自然语言完成记账/查询，系统负责意图解析、槽位补全、确认回显与校验。

## 1. 对话协议：一句话记账

### 1.1 处理流程（五步管线）

```
用户输入 → ①意图识别 → ②槽位抽取 → ③缺失槽位追问 → ④确认回显 → ⑤落库+校验
```

- **意图类型**：记支出 / 记收入 / **内部转账**（白名单账户间流转：工资卡→零用卡、活期→余额宝） / 报销到账 / 查询 / 对账 / 修正（微调） / **配置管理**（加分类、加账户、停用、改名、加别名、列表）。
  - 区分原则：转入方**在白名单内** → 内部转账（不产生收支统计）；转入**表外**（证券、外部理财） → 支出-投资；判断不确定时追问一句"转到哪张卡/哪里"。
- **槽位**：date、period、direction、category、amount、account、note。
- **默认与推断规则**（与 t1 §3.1 一致）：
  - date 缺省 = 今天；"昨天/上周五"等相对时间由解析器换算。
  - period 默认 = date 所在月；date 为月末 25 日后的工资周交易时**追问确认账期**。
  - direction 由关键词与分类联动推断（报销/工资/投资收益 → 收入）。
  - category 由商品词映射到 9 个支出/5 个收入白名单，不在白名单 → 追问。
  - account/category 由**别名表**推断（accounts/categories.aliases，经 addAliases 维护；如"平安卡"→平安银行、"猫粮"→宠物），而非硬编码映射；缺省追问或按最常用建议。
- **追问原则**：一次只问最关键的缺失槽位，给出带默认值的封闭式选项，用户可回"1/2/用默认"。金额缺失时必问；分类有歧义时列白名单候选。
- **确认回显**：落库前用紧凑单行/卡片回显七字段，标注推断项（标 *），用户回"对/改X"。
- **幂等**：60 秒内重复提交相同 (date, amount, account, category, note) → 提示"疑似重复，确认再记？"（t1 §3.3-3）。

### 1.2 场景示例

**场景 A：餐饮（U1 快速记账，槽位全，一步确认）**

> 用户：午饭和晚饭一共 58，微信
> 系统：📋 记支出确认
> - 日期*：2026-10-29（今天）｜账期*：2026-10
> - 分类*：餐饮美食｜金额：¥58.00｜账户：微信余额
> - 备注*：（午+晚餐合并）
> 回复"对"落库，或告诉我改哪项。
> 用户：对
> 系统：✅ 已记 2026-10 餐饮美食 ¥58.00（微信余额）

**场景 B：信用卡分期（U2）**

> 用户：招行信用卡分期买了漫步者耳机 1299，分12期
> 系统：📋 记支出确认
> - 日期*：今天｜账期*：本月｜分类*：数码电器｜金额：¥1,299.00｜账户：招行
> - 备注：信用卡分期：漫步者耳机 话费充值（12期）
> ⚠️ MVP 按现状一次性全额入账，不逐月拆期。回复"对"确认。
> 用户：对 → ✅ 已记（备注含"信用卡分期："前缀）

（若用户只说"刷信用卡买了个耳机1299"——缺账户归属：系统追问"走的招行卡吗？1. 招行（最常用）2. 其他账户"）

**场景 C：报销（U4）**

> 用户：上个月出差打车 320 的报销到账了，招行
> 系统：报销到账按"收入-报销收入"记。日期是今天到账吗？日期*：2026-10-29｜金额 ¥320｜账户 招行｜备注：出差打车报销。回复"对"。
> 用户：对 → ✅ 已记收入 报销收入 ¥320.00（招行）

**场景 D：转账/投资转入（U3）**

> 用户：转 5000 到余额宝买理财
> 系统：📋 记"支出-投资"（非消费，转出中行卡？）
> - 金额 ¥5,000｜分类：投资｜账户：中行*（转出方，请确认）｜备注：转入余额宝理财
> 注：余额宝在你的 8 账户白名单内；若转入证券等表外账户，仅备注记录。回复"对"。
> 用户：中行对 → ✅ 已记 2026-10 投资 ¥5,000.00（中行）

**场景 E：一句话信息不足 → 缺失槽位追问（AA/代付，U5）**

> 用户：昨天晚饭饭AA
> 系统：还缺金额。昨晚和谁 AA、总共多少、你付的哪个账户？
> 用户：一共 240，我微信先付的，人均 80
> 系统：📋 支出 餐饮美食 ¥80.00（你的份额）｜微信余额｜备注：饭AA（共240，先付后收）｜日期 2026-10-28
> 用户：对 → ✅

**场景 F：微信补差微调（U8）**

> 用户：微信补差 0.61，11月
> 系统：记支出 杂项 ¥0.61 微信余额，账期 2026-11*（跨月修正，确认账期）。对吗？
> 用户：对 → ✅

## 2. 查询与月度复盘对话示例（U6/U7）

**自然语言查询**

> 用户：这个月餐饮花了多少？
> 系统：2026-10 账期餐饮美食共 **¥1,287.50**（23 笔，笔均 ¥56），环比上月 -12%。最大单笔 ¥210（10-14 火锅 饭AA）。

> 用户：9月结余多少？各账户对得上吗？
> 系统：2026-09 收入 ¥21,580、支出 ¥8,342，结余 **¥13,238**。
> 账户勾稽（月末=月初+流入−流出）：中行 ✅ 招行 ✅ 微信 ✅ 建行 ✅ … 差异 0，全平。

**月度复盘（主动触发：账期结束后首次对话）**

> 系统：2026-10 账期已结束，要复盘吗？①分类支出排行 ②与上月对比 ③账户勾稽 ④投资/报销台账
> 用户：1
> 系统：TOP3：投资 ¥6,723 > 餐饮 ¥1,287 > 数码 ¥1,100 …（明细表）
> ⚠️ 勾稽发现：微信余额差 ¥0.61 → 可能是补差未记，回复"记一笔补差"即可生成 U8 修正。

## 3. DSH vs Claude Code 环境对比与推荐

| 维度 | DSH（Web GUI + run_code） | Claude Code（CLI + skill/CLAUDE.md） |
|------|--------------------------|--------------------------------------|
| 触发方式 | 浏览器打开 GUI 对话框，自然语言即触发；可声明文件/图片（账单截图 OCR） | 终端 `ledger 记账` / `ledger 月结` 命令或 slash command 触发 skill |
| 工具链 | run_code 直连 Python(openpyxl/pandas)，读写 xlsx、跑勾稽校验一体完成 | Claude Code 文件编辑+shell 脚本；skill 封装记账宏，CLAUDE.md 固化白名单与账期规则 |
| 交互形态 | 富卡片确认回显、可选按钮追问、结果内嵌表格，适合逐笔确认 | 纯文本回显，快捷但少按钮；适合熟练后快捷指令（"l 餐饮 58 微信"缩写语法） |
| 状态与上下文 | 会话内上下文长，月度复盘适合长对话；文件改动可 present 给用户下载 | CLAUDE.md 常驻规则、记忆稳定；但长对话复盘体验弱于 GUI |
| 校验能力 | run_code 内即时跑白名单/勾稽/幂等校验并返回差异报告 | 依赖脚本执行，同样可跑，但输出排版简陋 |
| 移动/随手记 | 浏览器随手开会话，拍照贴截图 OCR 记账是独有优势 | 需终端环境，随手性差 |

**推荐**：
1. **主环境选 DSH Web GUI**：确认回显、选项式追问、表格化复盘、截图 OCR 输入、run_code 直连账本校验，最契合"对话式记账+月度对账"的交互需求。
2. **Claude Code 作为进阶/熟练通道**：当用户形成固定记账语法后，用 skill 定义缩写命令（如 `/ledger add 餐饮 58 微信`）批量快捷录入与定时月结，作为效率补充。
3. 两环境共用同一 xlsx 数据与白名单规范（t1 §3），保证数据一致性；对话协议（本文件 §1）对两环境统一适用。

> 用户：猫粮 狗粮 洗牙
> 系统：✅ 已加支出分类"宠物"，别名：猫粮/狗粮/洗牙。以后"猫粮 45 微信"会自动归到宠物。

> 用户：对，再加 pab
> 系统：✅ 已加账户"平安银行"（别名：平安卡/pab）。该账户月初余额是多少？（用于本月勾稽）

**场景 I：停用/列表**

> 用户：对 → ✅ 已停用
> 用户：我的分类有哪些 → 系统调 listConfig 播报（停用项标注）。


**场景 J：内部转账（工资卡 → 零用钱卡）**

> 用户：转 2000 到零用钱那张卡
> 系统：📋 内部转账确认
> - 转出：招行（工资卡*）→ 转入：中行（零用钱卡*）｜¥2,000.00｜日期*：今天

**场景 K：表外投资 vs 内部转账的区分**

> 用户：转 5000 买理财
> 系统：转到哪里？1. 余额宝（账户内，记内部转账） 2. 证券/外部平台（记支出-投资）
> 用户：1
> 系统：✅ 按内部转账记：中行 → 余额宝 ¥5,000。不计入支出，月度复盘的消费排行不受影响。


## 5. 确认与纠错保障（设计铁律）

1. **逐笔确认，AI 不得静默落库**：五步管线中④确认回显是硬性关卡，任何记账/转账/配置变更必须用户回复"对"（或等价确认）后才调用写入接口；所有 AI 推断项在回显中标 *，用户可"改X"单点纠正。
2. **歧义必问，不猜测**：金额缺失必问；分类歧义列白名单候选；账户歧义给"最常用+其他"选项；转账 vs 表外投资、月末账期归属等方向性歧义一律追问（场景 B/K/F）。
3. **落库后纠错**：发现记错说"改一下刚才那笔/把刚才那笔删了" → 系统调 updateTransaction / voidTransaction，先回显修改前后对照，确认后执行；作废为软删除留痕。封账账期需先 reopenPeriod（系统主动提示），改完重新对账封账。
4. **批量录入（二期）确认策略**：OCR 账单/批量文本先解析为**候选清单预览**（表格逐行列出七字段+标 *），用户回复"对"整批原子落库，或指出某几行修正后再落；**禁止任何不经过预览确认的批量写入**。
5. **重复防护**：指纹命中即回显已有记录要求确认（t2 §2.1），防止一句重复。


## 6. 账目可视化与 Excel 导出对话

**场景 L：账目细节可视化**

> 用户：这个月钱都花哪了？
> 系统：（调 reportCategoryBreakdown）📊 2026-11 支出构成 ¥8,342：
> - 🥘 餐饮美食 ¥2,100 (25%) ｜ 🛒 日用百货 ¥1,650 (20%) ｜ 📱 数码电器 ¥1,200 (14%) …
> （DSH 环境同时渲染饼图卡片；回复"明细"看分类明细，回复"趋势"看近 6 个月对比）

> 用户：看下趋势
> 系统：（调 reportTrend）📈 近 6 个月支出：7月 ¥6.2k → 8月 ¥7.8k → … 11月 ¥8.3k，环比 +6%。收入线平稳在 ¥17k/月。

> 用户：微信这个月流水
> 系统：（调 reportAccountFlow）微信余额：流入 ¥3,400（含内部转入 ¥2,000）流出 ¥2,850，净 +¥550。要看逐笔明细吗？（reportDetail 表格，可翻页）

> 用户：哪些天花得多？
> 系统：（调 reportDailySpend）11 月消费热力：峰值 11-11 ¥1,299（漫步者耳机分期）。日均 ¥62。

**场景 M：Excel 导出**

> 用户：导出 10 月和 11 月的账
> 系统：（调 exportToXlsx）✅ 已生成 [2026下半年-导出.xlsx](data/export/…)：交易流水 96 笔 + 余额快照 + 配置表，与旧账本同构，Excel 可直接打开。
> 用户：再要一份分类透视
> 系统：（调 exportReportToXlsx kind=category）✅ 已生成 [分类透视-2026Q4.xlsx]：按账期×分类的支出透视表 + 占比列。

**设计约定**：所有可视化报表走 t2 的 `report*` 接口族（chart-ready JSON），DSH 侧负责渲染成卡片/图表，Claude Code 侧输出文本表格——**接口与渲染解耦**，未来接入任何可视化前端无需改数据层。
